## Iteration 1

### Verdict
**CHANGES_REQUESTED**

### Summary
Four of the five well-scoped library components (CSV source connector, ADLS Gen2
Parquet sink connector, `SsgPipeTransformer`, `SsgPipeDqChecker`) are individually
well-built: grading logic is genuinely table-driven and matches the spec exactly at
every boundary (verified independently against `grade_from_marks`), DQ never silently
drops a record, unit tests are thorough (95 tests, independently re-run and passing;
`ruff check`, `ruff format --check`, and `mypy --ignore-missing-imports` all pass
against `src`/`tests` in this environment), and no secret/credential literal was found
anywhere in code, infra, or example settings. However, this workstream is **not
functionally complete** and the DE Plan/DoD's own completion claims are inaccurate in
a material way: **the actual orchestrated pipeline does not exist.** DE Plan §4.6
(`src/pytiq/pipelines/ssgpipe/config.py`, `runner.py`, package `README.md`) was never
built by any of the five dispatched specialists — there is no code anywhere in the
repository that instantiates the three source connectors, calls the transformer, runs
DQ, and writes both sink outputs plus `run_summary.json` together. FR-SSGPIPE-15
("deliver a deployable, orchestrated pipeline covering read→validate→join→grade→DQ→
write valid→write rejected→emit metrics") is unimplemented, and consequently AC-1,
AC-3, AC-8, AC-9, AC-11, AC-12, and AC-13 — every acceptance criterion phrased as "when
the pipeline runs" — cannot currently be demonstrated at all, because there is nothing
to run. Compounding this, there is no `pyproject.toml` anywhere in the repository (a
hard, unconditional `DEPLOYMENT_STANDARDS.md` rule 1 violation) and no `Dockerfile`,
so the CI pipeline that Milinda built (`ci/ssgpipe-pipeline.yml`) would fail at its
very first step (`pip install -e .[dev]`) and its container build step has nothing to
build from. The SDD's own mandated lightweight data contract (§8, "a Pydantic model
... containing identity, schema/nullability, keys, and per-field sensitivity
classification") was never created either. Independently, I found a genuine
correctness/data-integrity defect in the sink's "atomic" publish: it deletes the
existing partition file before renaming the staged file into place, so a crash between
delete and rename leaves the partition **completely missing** (not merely
"half-written" as the module docstring and DoD both claim) — this is confirmed by the
connector's own test `test_crash_during_rename_does_not_corrupt_a_pre_existing_partition`,
whose assertion (`final_path not in crashing_client.store`) proves data loss on retry
of an unlucky crash, not the idempotent, always-available overwrite the SDD/Sink
Contract require. The DoD checklist itself needs correction: it claims "Every task in
the DE Plan `Files to Touch` section has been addressed" while never mentioning §4.6,
and marks the story implicitly complete/ready for review despite this. This is a
CHANGES_REQUESTED verdict — the individual components are strong, but the workstream
as a whole is not deliverable-complete, and one of the "never weakened" unconditional
correctness/idempotency rules is violated in the sink.

### Standards Compliance

1. `docs/development-standards/template/DataEnginnering/common-reference-dataops/` (no matching artifact exists) — *Standard:* `DEPLOYMENT_STANDARDS.md` rule 1 — *Trigger check:* unconditional; every PyTIQ package MUST declare PEP 621 metadata in `pyproject.toml` — **Problem:** no `pyproject.toml` exists anywhere in the repository for the `ssgpipe`/`pytiq` package; there is consequently no declared dependency list, no version, no entry points, and the `ci/ssgpipe-pipeline.yml`'s `pip install -e .[dev]` step has nothing to install. **Required change:** add a `pyproject.toml` at the package root (PEP 621 metadata, `[tool.ruff]`, `[tool.mypy]`, `[tool.pytest.ini_options]`, dependencies for `pandas`, `pyarrow`, `pydantic`, `azure-identity`, `azure-storage-file-datalake`, `simple_azure_utils`), plus a committed lock file per rule 4 (application project, not a library).

2. `ci/ssgpipe-pipeline.yml:69,128` (`pip install -e .[dev]`, `Dockerfile: '$(packageDirectory)/Dockerfile'`) — *Standard:* `DEPLOYMENT_STANDARDS.md` rules 1/7 — *Trigger check:* unconditional (CI gates are mandatory for production-deployed shared code, which this is) — **Problem:** both referenced artifacts (`pyproject.toml`, `src/pytiq/Dockerfile`) do not exist, so this pipeline cannot pass its own Build stage, let alone reach Release. **Required change:** create both files, or correct the DoD to reflect that CI has never actually been validated to run (DoD.22's claim that "gate wiring is reviewed... Sink-side and Source-side local gates independently verified green" does not establish that the pipeline as a whole executes).

3. `src/pytiq/pipelines/` (does not exist) — *Standard:* `DATA_ENGINEERING_STANDARDS.md` rule 1 (pipeline decomposition), FR-SSGPIPE-15, DE Plan §4.6 — *Trigger check:* unconditional — this workload has business transformation logic, three sources, and independent DQ gating, so the 4-stage architecture is mandatory (SDD §2 agrees) — **Problem:** the four stages are implemented as independent, unwired library modules; no orchestration code exists to run them as one pipeline. **Required change:** implement `src/pytiq/pipelines/ssgpipe/config.py` (typed `SsgPipeConfig` per `CONFIGURATION_STANDARDS.md`, matching SDD §13) and `runner.py` (wires 3× `CsvSourceConnector` → `SsgPipeTransformer` → `SsgPipeDqChecker` → 2× `ParquetPartitionSinkConnector` → `RunSummaryWriter`, plus the pre-flight health check referenced by `infra/ssgpipe/README.md` and `container-apps-job.bicep`'s own comments).

4. `src/pytiq/connectors/sink/parquet_partition_sink_connector.py:335-338` — *Standard:* `SINK_CONNECTOR_STANDARDS.md` rules 3/4 (atomicity: "partial-failure MUST leave the destination in its prior consistent state, not a half-written one") — *Trigger check:* unconditional (correctness/data-integrity is never subject to Proportionality) — **Problem:** `write()` calls `delete_path(final_path)` before `rename_path(staging_path, final_path)`. A crash between these two calls leaves `final_path` **absent**, not merely unchanged or half-written — this is a worse outcome than "half-written" and is proven by the connector's own test (`test_crash_during_rename_does_not_corrupt_a_pre_existing_partition`, whose only assertion is that `final_path not in crashing_client.store` after the simulated crash). This is NOT the "prior consistent state" the standard requires. **Required change:** use a rename operation that atomically replaces the destination (ADLS Gen2 `rename_file` supports specifying the destination path directly and the SDK/service call itself performs the swap without a separate delete — confirm the actual `azure-storage-file-datalake` rename semantics support overwrite, or use a manifest-pointer-swap pattern instead of delete-then-rename) so the final path is never in an "absent" state during publish.

5. `docs/data-engineering-design/2.1_SSGPIPE_SDD.md` §8 vs. `src/pytiq/` (no contract artifact) — *Standard:* `DATA_CONTRACT_STANDARDS.md` rules 1, 11, 12 — *Trigger check:* the SDD itself determined a lightweight contract IS warranted (external ADLS Gen2 delivery + PII), and explicitly committed to "a Pydantic model, colocated with the transformer" — this is not a Proportionality-exempted item, it is a design decision the SDD already made — **Problem:** no such model exists anywhere in the codebase; per-field sensitivity classification (SDD §11's table) is documented only in prose, not enforced/attached to any schema artifact DQ or drift detection could consume. **Required change:** add the Pydantic contract model (e.g. `src/pytiq/transformations/ssgpipe_contract.py` or colocated in the transformer module) matching `OUTPUT_COLUMNS`, with per-field classification metadata, per SDD §8's own stated design.

6. `src/pytiq/data_quality/ssgpipe_dq_checks.py:64` (`"grade_letter"` in `DEFAULT_REQUIRED_NOT_NULL_FIELDS`) — *Standard:* `DATA_QUALITY_STANDARDS.md` rule 2 (explicit severity/scope per check) — *Trigger check:* applies since this is a production-deployed, DQ-gated dataset — **Problem:** not a bug, but a design overlap worth flagging: `grade_letter` is null precisely when `marks` fails type/range, so every invalid-`marks` record is tagged with *two* overlapping reasons (`not_null_violation:grade_letter` and `marks_out_of_range`/`invalid_marks_type`). This inflates `not_null_violation_count`/`dq_failure_reasons` without a new root cause. Non-blocking as delivered (both reasons are still accurate), but flagged since it slightly muddies the FR-SSGPIPE-16 "invalid-marks count" metric's independence from the not-null count — **Required change (non-blocking, recommend before GA):** exclude `grade_letter` from the not-null required list (it is a derived field, not a source field) so its nullity is only ever explained via the marks-type/marks-range reasons, matching SDD §6's stated check list of "not-null on required fields per source's discovered schema" (a derived output column is not a *source* field).

### Proportionality Validation
- **Over-engineering check:** None found. The 4-stage decomposition, formal-enough contract intent, and production-grade security/observability are all correctly justified by the SDD's own stated triggers (config-driven multi-source future, real Container Apps Jobs deployment, PII presence) — this is not enterprise ceremony applied to a toy script. No unnecessary abstraction, plugin registry, or premature multi-environment machinery was found.
- **Under-engineering check:** **Failed.** Two genuine under-engineering gaps were found that the Proportionality principle does *not* excuse: (1) the missing orchestrated pipeline (`DATA_ENGINEERING_STANDARDS.md` rule 1 — a pipeline "MUST decompose into explicit stages" *and be wired together*; four unconnected library modules are not a pipeline) is a functional-completeness gap, not a scope reduction the DE Requirements ever authorized; (2) the sink's delete-then-rename atomicity defect is a correctness/data-integrity gap, which per `ENGINEERING_STANDARDS.md`'s Proportionality principle is **never** subject to proportionate relaxation regardless of the current 5/5/15-row dataset size. Both are blocking regardless of how small the current data volume is.
