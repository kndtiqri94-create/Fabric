## 1. Summary

Build a batch pipeline that ingests `sample_data/students.csv`, `sample_data/subjects.csv`,
and `sample_data/grades.csv`, validates and left-joins them on `student_id`/`subject_id`,
derives a configurable `grade_letter` from `marks` (90-100=A+, 80-89=A, 75-79=B+, 70-74=B,
60-69=C+, 50-59=C, <50=F, using the exact decimal value), runs a full DQ suite that quarantines
— never silently drops — bad records, and writes the valid and rejected datasets as Parquet to
Azure Data Lake Storage Gen2 (`year=YYYY/month=MM/day=DD/` partitions), authenticated via
Managed Identity/Key Vault only. Deploys to Azure Container Apps Jobs via Azure DevOps CI/CD,
emitting the FR-SSGPIPE-16 execution-metrics set on every run.

## 2. Architecture Recap

Per the SDD: a 4-stage pipeline (ingestion → staging/validation → transformation → publishing).
Full-snapshot batch load every run (no incremental/CDC state). One config-driven
`CsvSourceConnector` architectural model instantiated three times (Students/Subjects/Grades),
each with `SupportsSchemaDiscovery` for runtime join-key verification. One
`ParquetPartitionSinkConnector` model instantiated twice (valid + rejected), using
overwrite-by-ingestion-date-partition with a stage-then-atomic-rename publish for idempotency.
Transformation is a single `SsgPipeTransformer` (left join + `date_of_birth` normalization +
configurable grade calculation + forward-looking grade-mismatch detection). Full DQ check suite
(not-null, uniqueness on `grade_id`, type/range on `marks`, referential integrity) with
record-level FAIL→quarantine, never a whole-run abort on data content. A lightweight (not
multi-consumer-versioned) data contract governs the published output, with explicit per-field
PII/sensitivity classification. Security is Managed Identity/Key Vault only for ADLS Gen2 — no
literal storage account names/keys/SAS tokens/connection strings anywhere in code or config.

## 5. Data Movement & State Strategy

- Extraction mode(s): Full snapshot only, every run (no incremental/CDC — DE Requirements §4).
- Write mode(s): Overwrite by ingestion-date partition (truncate-reload within a partition,
  never append) for both the valid and rejected sinks.
- Watermark/checkpoint persistence: Not applicable — no incremental state exists.
- Idempotency mechanism (mandatory): overwrite-by-partition at the sink + a fully deterministic
  transformation (same source snapshot + same run date ⇒ byte-for-byte equivalent output, modulo
  the `pipeline_run_time` audit column). Stage-then-atomic-rename publish prevents a crash from
  leaving a half-written partition visible to readers.

## 7. Threat Model / Security Notes

- Secrets/credentials handling: CSV sources need no credentials (local file reads). The ADLS
  Gen2 sink uses **Managed Identity only** (`DefaultAzureCredential`, workload identity on the
  Container Apps Job) via a `SecretProvider`-shaped abstraction — no storage account name,
  access key, SAS token, or connection string is ever a literal in code or config. Non-secret
  connection details (storage account name, container name) resolve via Azure App Configuration
  or an untracked local settings file (`--settings-path`), matching the template's existing
  `simple_azure_utils.load_setting` convention.
- PII/sensitive data handling (DE Requirements §9 confirms PII is present): `first_name`,
  `last_name`, `date_of_birth`, `email` = Restricted/PII; `gender` = Confidential; `marks`,
  `grade_letter`, `grade_mismatch` = Confidential; `student_id`/`subject_id`/`grade_id`/
  `subject_name`/`subject_code`/`credits`/`exam_term` = Internal. No PII/restricted value may
  appear in any log line at any level (structured logs reference records by `grade_id`/`run_id`
  only) — the rejected Parquet dataset may retain the full record (that is its purpose) but only
  in the access-controlled ADLS Gen2 destination, never logged. Only the FR-SSGPIPE-4 minimum
  column set is extracted/persisted — no passthrough of arbitrary extra source columns.
- Environment separation: Not applicable — single-environment topology confirmed (PRD OQ12).

## 8. Test Strategy

- Unit tests (mandatory minimum, per the PRD's explicit test-coverage requirement FR-SSGPIPE-17):
  - Negative `marks` value → DQ range check fails, record routed to rejected, no grade assigned.
  - `marks` > 100 → same as above.
  - Null/missing `marks` → DQ not-null check fails, record routed to rejected, no grade assigned.
  - Missing student reference (`student_id` in Grades with no matching Students row) → DQ
    referential-integrity check fails, record routed to rejected.
  - Missing subject reference (`subject_id` in Grades with no matching Subjects row) → same.
  - Duplicate grade records (same `grade_id` appearing twice) → DQ uniqueness check fails; first
    occurrence kept, subsequent duplicate(s) routed to rejected with a `duplicate_record` reason.
  - `grade_from_marks()` boundary tests: exact boundary values per the grading table (e.g. 90.00,
    89.99, 80.00, 79.99, 75.00, 74.99, 70.00, 69.99, 60.00, 59.99, 50.00, 49.99) plus the example
    values from the requirement (92.00→A+, 88.50→A, 75.00→B+, 74.99→B, 69.50→C+, 50.00→C,
    49.99→F).
  - Schema-discovery failure: a source file missing an expected join key → connector raises a
    classified, clear error (not a silent mis-join).
- Integration tests: sink write + destination reconciliation against an ADLS Gen2 emulator or a
  test storage account/container (Kevin); re-running the same ingestion date twice produces the
  same valid/rejected partition contents (idempotency).
- Restart/recovery/idempotency tests: same-day re-run overwrite behavior (no duplication, no
  partial partition visible on a simulated mid-write crash).
- DQ tests: full check-suite coverage above, plus `run_summary.json` metric-count correctness
  (source counts, transformed count, rejected count, invalid-marks count, missing-join count,
  grade-mismatch count).

## 9. Observability

- Structured log events: JSON-capable structured logs carrying `pipeline_name`, `pipeline_id`,
  `run_id`, `stage_id`, `correlation_id`, timing, and status fields.
- Metrics (FR-SSGPIPE-16, emitted at run completion including on failure), persisted in
  `run_summary.json` with distinguishable `technical` and `data_quality` blocks: Students/
  Subjects/Grades source record counts, successfully-transformed count, total rejected count,
  invalid-`marks` count, missing-join-record count (Student↔Grade and Subject↔Grade counted
  separately), grade-mismatch count, pipeline start time, end time, overall status.
- Correlation: a `run_id`/`correlation_id` generated at run start, threaded through every
  connector/transformer/DQ/sink call.

## 10. Risks & Trade-offs

- R1: No numeric SLA/SLO exists (OQ-DE1) — mitigation: execution metrics are sufficient to
  operate without one for now; a future Product Owner decision, not an implementation gap.
- R2: No named downstream consumer (OQ4) — mitigation: the lightweight data contract (SDD §8) is
  built so it can be promoted to a full versioned contract without redesign once a consumer is
  named.
- R3: No retention/deletion policy for the PII-bearing ADLS Gen2 output (OQ-DE2) — mitigation:
  flagged to Shiham before the storage account's lifecycle policy is finalized in Milinda's
  infra work; not fabricated here.
- R4: The default DQ severity policy (record-level FAIL → quarantine, never whole-run abort) is a
  Data Architect default, not yet a ratified business decision — mitigation: documented as such,
  subject to Product Owner revision.

## 11. Out of Scope

- Real-time/streaming ingestion (PRD NG8).
- A monitoring dashboard/UI for pipeline runs or DQ reports (PRD NG9) — `run_summary.json` is a
  durable inspectable artifact, not a dashboard.
- Onboarding a specific downstream consumer (OQ4).
- Azure SQL/Google Sheets source connector implementations (OQ6) — only the config seam is built
  now (CSV connector behind the shared Connector Contract).
- A numeric run-completion SLA/SLO or missed-schedule alerting commitment (OQ-DE1).
- A ratified data retention/deletion policy for the ADLS Gen2 output (OQ-DE2).
- Multi-environment (DEV/QA/PROD) topology (PRD OQ12).
- A full, versioned, multi-consumer data contract with deprecation machinery (SDD §8/§16).
- Reporting/Power BI artifacts (Migara not required — see §3).
