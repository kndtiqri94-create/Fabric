# Solution Design Document 2.1 — Student/Subject/Grade Reporting Data Pipeline

- **Workstream:** E-2 — Student/Subject/Grade Reporting Data Pipeline (Data Engineering)
- **DE Requirements:** `docs/data-engineering-requirements/2_SSGPIPE_DE_REQUIREMENTS.md`
- **User Story:** `docs/user-stories/2.1_STUDENT_SUBJECT_GRADE_PIPELINE_USER_STORY.md`
- **Status:** Ready for Planning
- **Author:** Salinda (Data Architect)
- **Created:** 2026-08-25

## 1. Summary

A batch, full-snapshot pipeline ingests three CSV sources (Students, Subjects,
Grades), validates and combines them, derives a configurable letter grade per
result, and delivers a validated Parquet dataset (plus a separate rejected
dataset) to Azure Data Lake Storage Gen2, partitioned by ingestion date, running
unattended on Azure Container Apps Jobs via Azure DevOps CI/CD. Architectural
complexity is **deliberately split**: the current data (5/5/15 rows, one CSV
source) would alone justify a single-stage script, but three concrete triggers
from the DE Requirements' Proportionality Assessment (§12) push this to a
**4-stage architecture with a formal-enough contract, full DQ infrastructure,
and production-grade security/observability**: (1) FR-SSGPIPE-1/2 mandate a
config-driven, schema-inspecting source layer so Azure SQL/Google Sheets can
replace CSV without touching downstream code; (2) the workload is genuinely
production-deployed (Container Apps Jobs, Azure DevOps CI/CD, real ADLS Gen2);
(3) Student PII plus academic-record data triggers unconditional
`SECURITY_AND_PII_STANDARDS.md` classification regardless of row count.
Conversely, this design explicitly omits incremental/CDC state, multi-environment
separation, lineage tooling, and a monitoring dashboard — none are triggered.

## 2. Pipeline Architecture

- **Stage decomposition: 4-stage (ingestion → staging/validation → transformation
  → publishing).** Trigger for the full decomposition, per
  `DATA_ENGINEERING_STANDARDS.md` rule 1: this pipeline has business
  transformation logic (join + grade calculation), **three** sources, and an
  explicit requirement (FR-SSGPIPE-2, FR-SSGPIPE-5) to validate/DQ-gate
  independently of extraction and of the final write. A single-stage
  CSV→Parquet collapse is NOT proportionate here — that exemption is for pure
  format conversions with no business rules, which this is not.
  - **Ingestion**: three source connectors (Students, Subjects, Grades) each
    extract raw rows + runtime-discovered schema (§3).
  - **Staging/validation**: join-key presence check (FR-SSGPIPE-2) and DQ rule
    suite (§6) — required-field/null, duplicate, type/date, `marks` range,
    referential integrity. Failing records are tagged and set aside here, not
    silently coerced.
  - **Transformation**: Students+Subjects+Grades join, `date_of_birth`
    normalization, `grade_letter` derivation, source-grade mismatch check
    (§5).
  - **Publishing**: split into **valid** (graded, DQ-passed) and **rejected**
    (DQ-failed) datasets, both written as Parquet to ADLS Gen2, ingestion-date
    partitioned (§4), plus an execution-metrics/DQ-summary artifact.
- **Stage boundary contracts**: internal, single-pipeline boundaries (ingestion→
  staging, staging→transformation) use informal, typed contracts (Pydantic
  models/dataclasses) per `DATA_ENGINEERING_STANDARDS.md` rule 2 — no known
  external/cross-pipeline consumer of these intermediate boundaries exists. The
  **publishing-stage output** (the combined graded dataset in ADLS Gen2) gets a
  lightweight formal contract (§8) because it is externally delivered and
  carries PII — see §8 for why this boundary, and only this one, is formalized.
- **Batch / micro-batch / streaming model**: batch, on-demand/daily/weekly
  (FR-SSGPIPE-8). Streaming is explicitly out of scope (PRD NG8).
- **Full / incremental / CDC strategy**: **full snapshot per run** (DE
  Requirements §4) — every run re-reads all three sources in full and produces
  a fresh ingestion-date partition. No watermark/cursor/CDC state exists or is
  needed; see §7 for the resulting idempotency mechanism.

## 3. Source Connector Architecture

One connector architectural model is used — a generic, config-driven
`CsvSourceConnector` (Files/Object Storage category per
`SOURCE_CONNECTOR_STANDARDS.md`) instantiated three times (Students, Subjects,
Grades), each parameterized by its file path and expected column/join-key
configuration rather than three hand-written classes. This is the same
Connector Contract the template's `AzureSQLSourceConnector` /
`GoogleSheetSourceConnector` already implement — swapping a source later means
adding a new connector class behind the same contract, not redesigning the
pipeline (FR-SSGPIPE-1).

- **Connectivity check** (`SupportsConnectivityCheck`): **Not implemented.**
  Per the Connector Contract, a local/static file source MAY omit this — there
  is no remote endpoint to probe. A missing/unreadable file surfaces as an
  extraction-time fatal error instead (see §9).
- **Schema/metadata discovery** (`SupportsSchemaDiscovery`): **Required and
  implemented.** Trigger: FR-SSGPIPE-2 explicitly requires inspecting each
  source's actual schema at runtime (never hard-coding column names) precisely
  *because* the source category can change (CSV today, Azure SQL/Google Sheets
  later per FR-SSGPIPE-1) — this is the `DATA_ENGINEERING_STANDARDS.md` rule 14
  trigger ("the source's schema can change over the pipeline's lifetime"), even
  though the CSV schema is stable today. `discover_schema()` reads the CSV
  header row, confirms the entity's declared join key(s) are present
  (`student_id` for Students/Grades, `subject_id` for Subjects/Grades), and
  raises a classified, clearly-reported error if an expected key is missing or
  renamed (AC-2) rather than silently mis-joining downstream.
- **Incremental/checkpointed extraction** (`SupportsIncrementalExtraction`):
  **Not implemented.** Trigger for omission: DE Requirements §4 confirms full
  snapshot load only, every run — there is no watermark/cursor to manage. Each
  connector implements **Full** extraction mode only (baseline mode, per
  `SOURCE_CONNECTOR_STANDARDS.md` Extraction Modes table).
- **Files/Object Storage rules applied**: each connector reads one explicitly
  named file (no glob/discovery needed — one file per entity, not a
  drop-folder); encoding/delimiter are explicit configuration, not
  auto-detected; a corrupt/unparseable file is a run-level fatal error for that
  source (see §9) rather than a partial-file DQ concern, since malformed CSV
  structure (not malformed *row content*, which DQ handles) means the source
  cannot be meaningfully read at all.
- **Resource cleanup**: each connector's `extract()` wraps its own
  `with open(...)` — no connection/cursor is held open across calls, so no
  context-manager pair is required beyond that (Core Contract item 3's
  "nothing to release beyond a single scoped file read" exemption applies).
- **Extraction metrics**: emitted (records read per source) — mandatory per
  `SOURCE_CONNECTOR_STANDARDS.md` rule 6, since this connector is
  production-deployed (Container Apps Jobs).

## 4. Sink Connector Architecture

Two logical outputs share one generic `ParquetPartitionSinkConnector`
(destination category: object storage / ADLS Gen2), instantiated once for the
**valid** dataset and once for the **rejected** dataset, each targeting its own
path prefix.

- **Destination and write mode**: **Overwrite (partition-level truncate-reload)**.
  Each run writes to `.../{dataset}/year=YYYY/month=MM/day=DD/`, and the sink
  atomically replaces that specific partition's contents — never appends
  within a partition. This directly satisfies the DE Requirements' §6 "re-run
  same day = clean replacement, not duplication" expectation, and resolves
  §7/OQ7 (overwrite, not append, within a day) as the Data Architect default.
- **Retry safety classification** (`SINK_CONNECTOR_STANDARDS.md` Write Modes
  table): **Safe to retry as-is.** Overwrite-by-partition is idempotent by
  construction provided the swap is atomic (see mechanism below) — no
  additional dedup/merge-key mechanism is required.
- **Atomicity mechanism** (destination has no native transactions): stage-then-
  publish, with the swap direction **explicitly prescribed** (tightened in
  iteration 2 — see Change Log — after Ayodhya's review found a
  delete-then-rename implementation defect against the original wording). The
  sink writes the partition's Parquet file(s) to a temporary path under the
  same container (`.../{dataset}/_staging/{run_id}/...`). Publish is then a
  **single destination-replacing operation that makes the new content visible
  and the old content unavailable in the same step** — e.g. a rename/move call
  that targets the final `year=/month=/day=/` path directly and itself performs
  the overwrite (confirm and use the ADLS Gen2 rename API's actual
  destination-overwrite semantics), or, if that overwrite semantics cannot be
  confirmed, a manifest/pointer-swap pattern (write new content to a
  content-addressed path, then atomically repoint a single manifest/marker that
  readers resolve through). **The old partition's content MUST remain fully
  intact and readable at its path until the new content is durably staged and
  the swap step itself executes — deleting the old path as a step that
  precedes or is separate from the rename/swap is explicitly disallowed**,
  because a crash between an old-content delete and a new-content rename
  leaves the partition observably *absent* (worse than "half-written," and a
  direct violation of AC-15/DE Requirements §6's "never worse off than before
  the run started, holds either the complete previous output or the complete
  new output, never neither"). A crash before the swap step leaves only
  orphaned staging content and the pre-existing partition untouched; a crash
  after the swap step leaves the new partition complete — there is no crash
  window in which neither exists (`SINK_CONNECTOR_STANDARDS.md` rule 4).
- **Deterministic file naming**: file name is derived from the dataset name and
  ingestion date (not a random UUID), so a retried run recognizably replaces
  the same logical file (`SINK_CONNECTOR_STANDARDS.md` rule 8).
- **Schema-compatibility check**: **Trivial pass-through.** Each run
  creates/overwrites its own partition fresh — there is no prior data in that
  partition to reconcile against (`SINK_CONNECTOR_STANDARDS.md` rule 2
  exemption applies). The dataset's overall schema is still governed by the
  data contract (§8).
- **Destination validation / reconciliation**: **Required and implemented.**
  Trigger: this workload is production-deployed and its output is externally
  consumed (`SINK_CONNECTOR_STANDARDS.md` rule 9). After write, the sink
  re-reads the written partition's row count and reconciles it against the
  in-memory row count handed to `write()`, raising if they disagree.
- **Partial-batch failure handling**: **Not applicable within the sink** — by
  the time records reach this sink they have already been split into
  valid/rejected by the DQ stage (§6); each sink call is a single atomic
  Parquet write with no further per-record partial-failure mode
  (`SINK_CONNECTOR_STANDARDS.md` rule 5 exemption).
- **Write metrics**: rows written (valid), rows written (rejected), duration —
  emitted per run, mandatory since production-deployed.
- **Metrics/DQ-summary artifact**: a small structured JSON artifact
  (`_metrics/run_summary.json`) is written into the same ingestion-date
  partition alongside the valid dataset, containing the FR-SSGPIPE-16 counts —
  this resolves OQ9 (DQ report delivery) as a durable, inspectable artifact
  rather than log-only.

## 5. Transformation Placement

Business rules live in a single `SsgPipeTransformer`, isolated from both
connector and sink modules per `TRANSFORMATION_STANDARDS.md` rule 1.

- **Join**: Grades (driving/fact table) **left-joined** to Students on
  `student_id` and to Subjects on `subject_id`. Join type and cardinality are
  explicit and documented: many-to-one in both directions (many Grade rows per
  Student/Subject) — `TRANSFORMATION_STANDARDS.md` rule 10. A left join (not
  inner) is deliberate: a Grade row with no matching Student/Subject must
  **survive the join** as a null-populated row so the DQ referential-integrity
  check (§6) can detect and route it to rejected, rather than have the join
  silently discard it (which an inner join would do, defeating FR-SSGPIPE-5's
  "never silently drop" requirement).
- **`date_of_birth` normalization**: a single named function normalizes
  inconsistent input date formats into a proper date type (FR-SSGPIPE-3);
  unparseable values become an explicit DQ finding (§6), not a silently
  discarded/defaulted value (`TRANSFORMATION_STANDARDS.md` rule 7).
- **Grade calculation**: `grade_from_marks(marks, grading_table)` — a single
  named, unit-testable function (`TRANSFORMATION_STANDARDS.md` rule 12) driven
  by a **configurable, ordered grading table** (FR-SSGPIPE-11), not hard-coded
  branching:

  | Range (inclusive lower, exclusive upper except top) | Letter |
  |---|---|
  | 90 ≤ marks ≤ 100 | A+ |
  | 80 ≤ marks < 90 | A |
  | 75 ≤ marks < 80 | B+ |
  | 70 ≤ marks < 75 | B |
  | 60 ≤ marks < 70 | C+ |
  | 50 ≤ marks < 60 | C |
  | marks < 50 | F |

  Evaluated against the exact decimal `marks` value, no rounding (74.99 → B).
  Only records that have already passed the `marks` DQ check (§6) reach this
  function — an invalid `marks` value is never passed to it.
- **Grade-mismatch detection (FR-SSGPIPE-13, forward-looking)**: if the joined
  record carries a source-supplied `grade`/`grade_letter` value (none exists in
  the current CSV schema — this branch is dormant today but implemented and
  tested per AC-6/FR-SSGPIPE-17), the transformer independently computes
  `grade_letter` via the same function above and emits a `grade_mismatch`
  finding (not a silent overwrite) whenever the two disagree.
- **Null handling / dedup**: null-handling is explicit per field (documented in
  the transformer's docstring — required fields fail DQ, optional fields
  propagate as null); duplicate-record dedup key is `grade_id` (tie-break: first
  occurrence in source order is flagged, all duplicates beyond the first are
  routed to rejected with a `duplicate_record` reason) — `TRANSFORMATION_STANDARDS.md`
  rule 8, resolving DE Requirements §8's open "exact duplicate-detection key"
  question as the Data Architect default.
- **Output columns**: exactly the FR-SSGPIPE-4 minimum set plus `grade_letter`,
  `grade_mismatch` (bool, nullable), `ingestion_date`, and the template's
  mandatory `audit_digest`/`pipeline_run_time` (via `AuditHelper.add_audit_columns`,
  applied before the sink boundary per `template/DataEnginnering/AGENTS.md`) —
  no passthrough of arbitrary extra source columns (`TRANSFORMATION_STANDARDS.md`
  rule 5).

## 6. Data Quality Placement

**Triggered and required in full** — per `DATA_QUALITY_STANDARDS.md` rule 1,
this dataset is both production-deployed and (per DE Requirements §7)
delivered to a destination intended for external consumption.

- **Checks implemented** (all record-level except where noted), each declared
  in configuration with an explicit severity policy per
  `DATA_QUALITY_STANDARDS.md` rule 2:
  - Not-null on required fields per source's discovered schema (all columns
    except none currently optional).
  - Uniqueness: no duplicate `grade_id` (§5).
  - Type validation: `marks` numeric, `date_of_birth` a valid date.
  - Range validation: `marks` within 0–100 inclusive (FR-SSGPIPE-12).
  - Referential integrity: every Grade row's `student_id` resolves to a
    Student row; every `subject_id` resolves to a Subject row
    (FR-SSGPIPE-5/17).
  - Business rule: `grade_mismatch` flag from §5 (informational, non-blocking).
- **Outcome model**: every check yields PASS/WARN/FAIL. **Default severity
  policy (resolving OQ5, non-blocking per DE Requirements §11):** every
  record-level check failure is `FAIL` at the record level and routes that
  record to the rejected dataset — **no record-level DQ finding ever aborts the
  whole run.** A **dataset-level** halt applies only to a genuine run-level
  failure (a source file missing/unreadable, or a join key confirmed absent at
  schema-discovery time per §3) — never to data-content violations. This
  matches FR-SSGPIPE-5's "detect and report, never silently drop, partial
  success expected" model and is flagged to Shiham (Product Owner) as a
  default subject to revision, not a business decision made unilaterally.
- **Quarantine mechanism**: every rejected record retains its original payload,
  the specific failing check(s), and the pipeline `run_id`
  (`DATA_ENGINEERING_STANDARDS.md` rule 20), written to the rejected Parquet
  dataset (§4) — never dropped.
- **Thresholds**: `marks` range bounds and the grading table are versioned
  configuration values (§13), not hardcoded — `DATA_QUALITY_STANDARDS.md` rule 5.
- **DQ result persistence and metrics**: required (rule 1's condition holds) —
  persisted in the `run_summary.json` artifact (§4) with per-check
  outcome/counts, and emitted as metrics distinct from technical/execution
  metrics (`OBSERVABILITY_STANDARDS.md` rule 7).
- **Owner**: the Data Engineer/Pipeline Operator persona is the documented
  triage owner for DQ findings, pending a named production data owner (DE
  Requirements §10 governance gap, non-blocking).

## 7. Restart / Recovery / Replay / Backfill

- **Restart behavior**: the pipeline is a single, full-snapshot run with no
  mid-run checkpoint (DE Requirements §6 confirms no in-run resume requirement
  at current volume). A crashed run is simply re-triggered on-demand; because
  every stage is deterministic given the same source snapshot (§9) and the sink
  writes are overwrite-by-partition (§4), a re-run produces the same valid
  output-cleanly replacing that day's partition, not appending duplicates.
- **Replay/backfill mechanism**: there is no separate backfill code path,
  because there is no historical incremental window to replay (DE
  Requirements §4/§6) — "replay" here means re-triggering the same full-run
  code path for the same or a different day, which is already the on-demand
  execution mode (FR-SSGPIPE-8). This satisfies
  `DATA_ENGINEERING_STANDARDS.md` rule 7 (same code path for backfill as normal
  processing) trivially, since there is only one code path.
- **Concurrent full reprocessing safety** (`DATA_ENGINEERING_STANDARDS.md` rule
  8): two overlapping runs for the *same* ingestion date are not supported
  (single-run assumption per DE Requirements §2 Concurrency) — the Container
  Apps Job trigger configuration (§14) MUST NOT allow overlapping executions
  for the same scheduled slot; this is an infra-level constraint, not
  additional pipeline logic.

## 8. Schemas / Contracts / Schema Evolution

- **Contract required? Yes, but lightweight — not a formal, multi-consumer,
  independently-versioned artifact.** Per `DATA_CONTRACT_STANDARDS.md` rule 1,
  a formal contract is warranted once a dataset "crosses a stage boundary
  consumed by more than one pipeline, or is published to a serving layer." No
  named external consumer exists yet (PRD OQ4, unresolved/non-blocking), so
  this is not yet a negotiated, multi-consumer contract with deprecation
  machinery. However, DE Requirements §10 correctly flags that the *published
  ADLS Gen2 output* — carrying PII and delivered to a real cloud destination
  intended for downstream use — should not be treated as a throwaway ad hoc
  schema. **Design decision**: define the combined/graded output as a single
  machine-readable schema (a Pydantic model, colocated with the transformer per
  `DATA_CONTRACT_STANDARDS.md` Recommended Practices) containing identity,
  schema/nullability, keys, and **per-field sensitivity classification**
  (§11) — satisfying the contract's minimum content without the full
  versioned-consumer-migration apparatus that only applies once real consumers
  are onboarded (§16/§19 note this as future work). **Ownership (made explicit
  in iteration 2 — see Change Log):** this Pydantic contract model is
  **Madhushika's (Transformation Developer) deliverable**, built alongside
  `SsgPipeTransformer` in the same `transformations/` root
  (`implementationRoots.transformations` in `core-config.yaml`) — it was
  correctly specified here in iteration 1 but never implemented; this is an
  implementation gap against an already-clear design decision, not an SDD
  ambiguity. §11's classification table is the source of truth the model's
  per-field metadata must reflect.
  - Identity: `ssgpipe.student_subject_grade` (v1).
  - Owner: Data Engineering (interim; no named production owner yet — DE
    Requirements §10).
  - Producer: `SsgPipeTransformer` / `ssgpipe` pipeline runner.
  - Known consumers: none named yet (OQ4).
  - Keys: `grade_id` (business key).
  - Uniqueness: `grade_id` unique (enforced by DQ, §6).
- **Schema drift detection required?** **No — omitted, with an explicit
  trigger check.** `DATA_ENGINEERING_STANDARDS.md` rule 14 requires drift
  detection when "the source supports schema discovery or its schema can
  change over the pipeline's lifetime." The CSV sources *do* implement
  `SupportsSchemaDiscovery` (§3) for the join-key-presence check, but that
  check is a **fail-fast presence/rename guard** (AC-2), not full drift
  classification (additive vs. breaking column changes) against a versioned
  contract — building full drift classification now, before a second source
  type is actually onboarded, would be premature machinery for a schema
  confirmed stable today (DE Requirements §1). This is deliberately narrower
  than rule 14's full scope and is flagged here as an explicit, reviewed
  scoping decision, not an oversight: when Azure SQL/Google Sheets substitution
  actually happens (OQ6), full drift classification against this v1 contract
  becomes mandatory at that time.

## 9. Idempotency and Failure Boundaries

- **Idempotency mechanism** (mandatory — `ENGINEERING_STANDARDS.md` rule 7,
  since retries/reprocessing are possible via on-demand re-trigger): overwrite-
  by-ingestion-date-partition at the sink (§4), combined with a fully
  deterministic transformation (§5/§9) — same source snapshot + same run date
  ⇒ byte-for-byte equivalent valid/rejected output
  (`DATA_ENGINEERING_STANDARDS.md` rule 9), modulo the `pipeline_run_time`
  audit column, which is isolated to metadata (not a business column).
- **Record-level vs. run-level failure handling**: record-level DQ failures
  (§6) are quarantined, never abort the run. Run-level failures are limited to:
  a source file missing/unreadable (connector-level fatal error, §3), an
  expected join key confirmed absent at schema-discovery time (§3, AC-2), or a
  sink write/reconciliation failure (§4) — each of these halts the run with a
  clear, non-silent error and `status=failure` in the emitted metrics (§12),
  per `DATA_ENGINEERING_STANDARDS.md` rule 19.

## 10. Partitioning and Performance/Scale

- **Size assumption stated explicitly**: current actual volume is 5 Students, 5
  Subjects, 15 Grades — trivially small and safely loadable fully into memory
  with `pandas` today, consistent with the existing `common-reference-dataops`
  template's pattern. Per `PERFORMANCE_AND_SCALE_STANDARDS.md` rule 1 and the
  DE Requirements' explicit NFR ("avoid unnecessary full in-memory loads" as a
  framework property, not a today's-data property), the connector/transformer
  boundary is designed so a future high-volume Azure SQL source can switch to
  chunked/server-side-cursor extraction (`SOURCE_CONNECTOR_STANDARDS.md` →
  Databases) without changing the transformer's contract — this is a forward
  compatibility property of the interface, not something built now.
- **Partitioning strategy**: output partitioned by ingestion date
  (`year=YYYY/month=MM/day=DD/`) per FR-SSGPIPE-14 — this is a **business
  requirement** (distinguishing each run's output), not a performance-driven
  partitioning decision, and applies regardless of current row count.
- **Streaming/chunking**: not implemented at this volume (see size assumption
  above) — full in-memory read/transform/write per run is proportionate today.
- **Concurrency/rate limits**: not applicable — local file reads, no rate
  limits; single-run-at-a-time assumption (§7).

## 11. Security / PII

**PII/sensitive data present: Yes** (Student `first_name`, `last_name`,
`date_of_birth`, `email`; academic-record data `marks`/`grade_letter`). Per
`SECURITY_AND_PII_STANDARDS.md`'s explicit exemption from Proportionality, every
rule below is unconditional given this workload's data.

- **Per-field sensitivity classification** (data contract §8, satisfying
  `SECURITY_AND_PII_STANDARDS.md` rule 11 — no field defaults to
  "unclassified"):

  | Field(s) | Classification |
  |---|---|
  | `first_name`, `last_name`, `date_of_birth`, `email` | Restricted/PII |
  | `gender` | Confidential |
  | `marks`, `grade_letter`, `grade_mismatch` | Confidential (sensitive student-record data) |
  | `student_id`, `subject_id`, `grade_id`, `subject_name`, `subject_code`, `credits`, `exam_term` | Internal |
  | `ingestion_date`, `audit_digest`, `pipeline_run_time` | Internal (metadata) |

- **Credential/secret handling**:
  - CSV sources today: no credentials — plain local file reads (DE
    Requirements §1). No `SecretProvider` needed for this connector today.
  - ADLS Gen2 sink: **Managed Identity only** (workload identity assigned to
    the Container Apps Job), resolved through a `SecretProvider`-shaped
    abstraction wrapping `DefaultAzureCredential` — no storage account name,
    access key, SAS token, or connection string is ever a literal in code or
    config (FR-SSGPIPE-14). Where a key/connection detail must still be
    externalized (e.g., storage account name, container name — not secrets
    themselves), it resolves via Azure App Configuration or an untracked local
    settings file (`--settings-path`), matching the template's existing
    `simple_azure_utils.load_setting` convention (FR-SSGPIPE-10).
  - Any future Azure SQL/Google Sheets source connector resolves its
    credentials the same way, per the existing template pattern — not
    re-invented per source.
- **Data minimization**: only the FR-SSGPIPE-4 minimum column set is
  extracted/persisted — no passthrough of arbitrary extra source columns
  (§5), satisfying rule 13.
- **Logging**: no PII/restricted value (including in the rejected-record
  quarantine payload's *logged* representation) appears in any log line at any
  level — the rejected Parquet dataset itself may retain the full record (that
  is its purpose, and it is written to the same access-controlled ADLS Gen2
  destination, not logged) but structured logs reference records by
  `grade_id`/`run_id`, never by name/email/date_of_birth.
- **Environment separation**: **Not applicable** — DE Requirements confirm a
  single-environment topology (PRD OQ12); `SECURITY_AND_PII_STANDARDS.md` rules
  9/10 and `DATA_ENGINEERING_STANDARDS.md` rule 23 apply only once a second
  environment exists.
- **Retention/deletion**: **Unresolved (OQ-DE2, non-blocking for this SDD)** —
  no retention period has been specified by the business for the ADLS Gen2
  output or rejected-record set. This SDD does not fabricate a retention
  policy; it is flagged to Shiham (Product Owner) before the storage account's
  lifecycle policy is finalized in the DevOps/infra implementation, per DE
  Requirements §9/§11.

## 12. Observability

**Triggered and required in full** — production-deployed on Container Apps
Jobs (`OBSERVABILITY_STANDARDS.md` rule 1/4/5/8/12 all apply).

- **Structured logging**: JSON-capable structured logs (not free-form string
  interpolation), carrying `pipeline_name`, `pipeline_id`, `run_id`,
  `stage_id`, `correlation_id`, timing, and status fields per the Standard
  Context Fields table.
- **Metrics** (FR-SSGPIPE-16, the authoritative minimum set — emitted at run
  completion, including on failure per `OBSERVABILITY_STANDARDS.md` rule 6):
  source record counts (Students/Subjects/Grades), successfully-transformed
  count, total rejected count, invalid-`marks` count, missing-join-record count
  (Student↔Grade / Subject↔Grade, separately), grade-mismatch count, pipeline
  start time, end time, and overall status. Persisted in `run_summary.json`
  (§4/§6) — resolving OQ9's "where is the DQ/execution report delivered"
  question as a durable artifact, distinct from a dashboard (explicitly out of
  scope per PRD NG9).
- **Technical vs. DQ metrics**: kept in distinguishable sections of
  `run_summary.json` (a `technical` block vs. a `data_quality` block), per
  `OBSERVABILITY_STANDARDS.md` rule 7.
- **Correlation**: a `run_id`/`correlation_id` is generated at run start and
  threaded through every connector/transformer/DQ/sink call.
- **Lineage**: derivable from `run_summary.json` (which run produced which
  ingestion-date partition, from which source snapshot) — no dedicated lineage
  tool required, satisfying `DATA_ENGINEERING_STANDARDS.md` rule 18 at the
  level this workload's production status requires.
- **Dashboards/alerting**: **not built** — explicitly out of scope (PRD NG9).
  `OBSERVABILITY_STANDARDS.md` rules 10/11 only bind once a dashboard/alerting
  is actually configured; none is here.

## 13. Configuration

- **Typed configuration model: required.** Trigger
  (`CONFIGURATION_STANDARDS.md` rule 1): the configuration surface spans three
  source paths, join-key mappings, output paths, DQ thresholds, the grading
  table, and the schedule — well beyond a "two-argument script," is reused
  across three connector instances, and is production-deployed. A Pydantic
  settings model is used, validated at startup/construction
  (`CONFIGURATION_STANDARDS.md` rule 2) — a missing required source path or an
  invalid grading-table entry fails immediately with a clear error, not
  mid-run.
- **Configuration domains kept separate** (rule 5, triggered by the
  multi-connector/multi-threshold surface): connector config (per-source file
  path, expected schema), pipeline config (join keys, DQ thresholds, grading
  table, output paths/partitioning), and runtime config (log level, run mode —
  on-demand/daily/weekly). This directly satisfies FR-SSGPIPE-7's "externalize
  everything, none hard-coded" requirement.
- **Secrets vs. configuration**: no secret literal ever appears in the typed
  config model or its defaults (rule 9); the ADLS Gen2 storage account
  identity is resolved via Managed Identity at runtime, not stored as config at
  all.
- **Environment separation**: **Not applicable** — single environment
  confirmed (PRD OQ12); rule 6 does not apply until a second environment
  exists.
- **Schedule**: on-demand/daily/weekly mode is a pipeline-config value,
  independent of validation/transformation/DQ logic (FR-SSGPIPE-8, AC-11) —
  changing it never requires a code change. Default timezone: **UTC**
  (resolving OQ8 as the Data Architect default, non-blocking).

## 14. Deployment Implications

- **Deployment target**: **Azure Container Apps Jobs** — already resolved by
  the stakeholder (PRD OQ10, confirmed 2026-08-24), not re-litigated here. This
  choice is consistent with the existing `common-reference-dataops` template's
  shape: the template is a plain Python package with argparse-driven runner
  entry points (`python -m runners.domain_runners....`), not a workflow-graph
  orchestrator (ADF/Synapse/Databricks) — a Container Apps Job is a natural,
  low-ceremony fit for "run this Python package's entry point on a schedule or
  on demand," matching NG12's deferral of orchestration-service choice to this
  document. A **scheduled trigger** covers daily/weekly modes; **manual job
  execution** (`az containerapp job start` or equivalent) covers on-demand
  (FR-SSGPIPE-8/AC-11/AC-12).
- **CI/CD**: **Azure DevOps Pipelines** (PRD OQ11, confirmed). Build stage:
  `ruff format --check`, `ruff check`, `mypy`, `pytest`, dependency/secret
  scanning (all blocking gates per `DEPLOYMENT_STANDARDS.md` rules 7–9, since
  this is production-deployed shared code) — matching
  `common-reference-dataops/README.md`'s existing tooling convention. Release
  stage: build one container image, push to a registry, deploy/update the
  Container Apps Job definition.
- **Environment topology**: **single environment** (PRD OQ12, confirmed) — no
  DEV→QA→PROD promotion machinery; `DEPLOYMENT_STANDARDS.md` rules 16/18
  (multi-environment promotion validation, PROD approval gate) do not apply
  since there is only one environment. A basic merge-to-deploy gate (all CI
  checks green) is sufficient.
- **Health check**: **required** (`DEPLOYMENT_STANDARDS.md` rule 14 — production-
  deployed, scheduled/long-running). Before running the pipeline logic, the job
  entry point performs a pre-flight check: all three source files are readable,
  and Managed Identity can resolve an ADLS Gen2 token — failing fast with a
  clear error if either check fails, rather than failing deep inside
  transformation.
- **Rollback**: **required** (`DEPLOYMENT_STANDARDS.md` rule 15 — production-
  deployed). Redeploying the previous container image tag to the Container
  Apps Job is the documented rollback path; no data migration is involved since
  every run overwrites its own partition idempotently (§7/§9).

## 15. Cloud / Vendor Boundaries

- **Portability**: the source layer is deliberately vendor-neutral behind the
  Connector Contract (§3) — CSV today, Azure SQL/Google Sheets later, with zero
  change to the transformer/DQ/sink code (FR-SSGPIPE-1). The **sink is
  intentionally Azure-specific** (ADLS Gen2, Managed Identity) — this is an
  explicit business requirement (FR-SSGPIPE-14), not an oversight; if a future
  requirement demands a different destination, that swap happens behind the
  same Sink Contract (§4), not by rewriting the transformer.
- **Vendor-specific code isolation**: all ADLS Gen2 SDK usage and
  `DefaultAzureCredential` resolution stay inside the sink connector; all CSV
  parsing stays inside the source connectors; the transformer and DQ modules
  import neither (`TRANSFORMATION_STANDARDS.md` rule 1).

## 16. Dependencies

- **Upstream**: none — this is the founding workstream (E-2) for this pipeline
  family; F-2.1 through F-2.6 are delivered together.
- **External systems**: the three sample CSV files (`sample_data/students.csv`,
  `sample_data/subjects.csv`, `sample_data/grades.csv`); an ADLS Gen2 storage
  account (to be provisioned); a Container Apps environment; Azure DevOps for
  CI/CD; Azure App Configuration (or local settings file) for non-secret
  connection configuration.
- **Downstream**: none named yet (PRD OQ4) — this design produces a
  consumer-agnostic, contract-described (§8) Parquet dataset; onboarding a real
  consumer later may require promoting §8's lightweight contract to a full,
  versioned, multi-consumer contract per `DATA_CONTRACT_STANDARDS.md` — flagged
  as future work, not built speculatively now (`ENGINEERING_STANDARDS.md` rule
  12).
- **Package/implementation root**: this pipeline is instantiated by copying
  `docs/development-standards/template/DataEnginnering/common-reference-dataops/`
  and renaming its `domain_*` scaffolding to the `ssgpipe` domain (per that
  template's README), adding a new `data_quality/` module (not present in the
  original template, since its Azure-SQL-to-Azure-SQL use case had no DQ gate)
  alongside `connectors/`, `transformations/`, `helpers/`, and `runners/`. The
  exact repository root for this new package is a Team Lead/DevOps Plan
  decision (per `core-config.yaml`'s note that `implementationRoots` are
  provisional and MUST be validated against the actual PyTIQ codebase before
  creation) — not fixed by this SDD.

## 17. Risks / Trade-offs / Assumptions

- **R1: No numeric SLA/SLO exists (OQ-DE1).** Mitigation: FR-SSGPIPE-16's
  execution metrics are sufficient to operate without one for now; if
  operational monitoring commitments are wanted later, that is a Product Owner
  decision, not an architecture gap.
- **R2: No named downstream consumer (OQ4).** Mitigation: the lightweight
  contract (§8) is deliberately built so it can be promoted to a full versioned
  contract without a redesign once a consumer is named.
- **R3: No retention/deletion policy for PII-bearing output (OQ-DE2).**
  Mitigation: flagged to Shiham before the storage account's lifecycle policy
  is finalized; not fabricated here.
- **R4: Default DQ severity policy (§6, resolving OQ5) is a Data Architect
  default, not a ratified business decision.** Mitigation: explicitly
  documented as a default subject to Product Owner revision, not silently
  assumed.
- **Assumption A1**: the current CSV schemas (DE Requirements §1) remain
  stable for this delivery; schema-discovery (§3) is the compensating control
  if that assumption breaks.
- **Assumption A2**: single-run-at-a-time execution (no concurrent runs of this
  pipeline) — enforced at the Container Apps Job trigger-configuration level
  (§7), not in pipeline code.

  consumer-agnostic dataset only.
- Deciding target production source locations beyond the current CSV sample
  (OQ6) — the config seam (§3) is built now; the actual Azure SQL/Google
  Sheets connector implementations are not.
- A numeric run-completion SLA/SLO or missed-schedule alerting commitment
  (OQ-DE1).

  (OQ-DE2) — flagged, not decided, here.

  resolved single-environment decision (PRD OQ12).
- A full, versioned, multi-consumer data contract with deprecation machinery
  (§8/§16) — the lightweight v1 contract defined here is sufficient until a
  real consumer is named.
